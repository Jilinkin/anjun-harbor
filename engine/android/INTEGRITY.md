# Release integrity standard

Each static release must compute SHA-256 from trusted built JAR bytes, verify the published bytes, then run integrity_release.py with a pinned publication commit and the trusted SHA-256. This reusable second-stage tool produces the optional config-md5.json and config-cn-md5.json, md5.txt and integrity.json. Publication workflows must run the generator for each new version after its binary is committed; RC2 has an automated workflow. Existing original configurations remain untouched. New releases require a new version path.

The reference takagen99/Box client source (ApiConfig.loadJar and JarLoader.loadJarInternal) parses ;md5; and can compare cached files, but the examined fresh download paths call the loader without a second digest check. Some cache modes bypass the comparison. Therefore the hint is not an enforced security check. Actual installed client is unidentified. MD5 is not a secure signature; an untrusted proxy can modify both the config and binary. Do not execute an unverified downloaded binary. The strongest practical distribution is direct trusted HTTPS hosting or a host that independently checks a trusted SHA-256/signature before executing. A checksum inside an untrusted JAR cannot protect its own loading. No server requirement is introduced.
